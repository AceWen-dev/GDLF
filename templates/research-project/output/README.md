# Output

Generated experiment results:

```text
output/
  INDEX.md        # generated front door: funnel + experiments + shortlist + claims
  runs/           # run directories (manifest, config, metrics, logs, checkpoints, evals)
  sweeps/         # sweep records, trial logs/results
  test_access/    # append-only test-set access log
  candidates/     # human-authored shortlist (small JSON, commit it)
  claims/         # reported claims (small JSON, commit it)
  reports/        # generated Markdown reports (rebuildable)
  scratch/        # disposable by definition; never cited by claims or INDEX
```

## Provenance classes

A file's location is decided by **where it comes from**, not by what it is
about. Every file under `output/` belongs to exactly one class:

| Class | Dirs | Who writes | Editable? | Lifecycle | Commit? |
|---|---|---|---|---|---|
| Recorded | `runs/`, `sweeps/`, `test_access/` | DLEF only | never | immutable; `dlef gc` | no |
| Judged | `candidates/`, `claims/` | you, via the tools | only via `candidates.py` / `ClaimStore` | status lifecycle | yes (small) |
| Rendered | `INDEX.md`, `reports/` | `make index` / `make report` | never by hand | delete freely, regenerate | no |
| Scratch | `scratch/` | anyone | freely | may vanish any time | no |

Two rules keep this honest:

1. **Judged registries are owner-approved.** A run set enters `candidates/`, a
   number enters `claims/`, and any status change requires the owner's explicit
   approval, recorded in `approved_by`. Agents propose the exact command and
   wait; they never approve their own. The report and INDEX show the approver,
   and records without one are flagged.
2. **Rendered views are never hand-edited.** If the front door is stale, run
   `make index`; if the report is stale, run `make report`. A hand-maintained
   overview always goes stale and then lies.

`candidates/` and `claims/` are the only human-authored folders; all other
folders are generated by DLEF or disposable by convention.

A run's training log is `logs/train.log`: timestamped epoch/step/eval/checkpoint
lines for humans. The machine-readable metrics stream is `metrics.jsonl`. A
sweep additionally captures each child process stdout/stderr in
`sweeps/<sweep_id>/trials/<trial_id>.log`.

Run directories are generated by DLEF; never edit them by hand. Retention is
handled by `dlef gc`, not manual deletion. Checkpoints, eval records and any
other files live inside the run directory; there is no second artifact copy.

A run directory contains:

```text
output/runs/<project>/<experiment>/<run_id>/
  manifest.json
  config.resolved.json
  metrics.jsonl
  logs/train.log
  tensorboard/          # when tensorboard.enabled=true
  checkpoints/
  evals/
```

The `output_root` config field controls the top-level path (default
`output`); relative values resolve against the project root. For `tools/` and
the Makefile, use `OUTPUT=<path>` or export `DLEF_OUTPUT_ROOT=<path>`.

## Finding a run

Start at the front door — `INDEX.md` is generated, so it never lies about the
current state:

```bash
make index
cat INDEX.md
```

Then drill down. Runs are grouped by project and experiment:

```text
output/runs/<project>/<experiment>/<run_id>/
```

Start with the experiment summary, then drill down:

```bash
make runs                                              # one row per experiment
make runs-all                                          # one row per run
python core/tools/runs.py --experiment baseline
python core/tools/runs.py --status completed --since 2026-10-01
python core/tools/runs.py --tag baseline
python core/tools/runs.py --json
python core/tools/run_info.py --run <run_id>
```

The summary shows, per experiment: run count, latest run, status, last metric,
best metric, tags and the last config source. `runs.py` is read-only; it never
edits a manifest. `run_info.py` then shows one run's config → source files.

For curves, start TensorBoard over the same root:

```bash
tensorboard --logdir output/runs --port 6006
# remote: tensorboard --logdir output/runs --port 6006 --bind_all
```

TensorBoard is a mirror; the files above remain the record.

## Shortlist before claims

Runs pile up faster than reports. Pull the few worth thinking about into
`output/candidates/`; the rest stay in the run store but leave your working set:

```bash
python core/tools/candidates.py add \
  --id <candidate-id> --title "<one line>" \
  --run <run1> --run <run2> \
  --metric <val-metric> --reason "<why this is worth studying>" \
  --approved-by "<owner, date: approval quote>"
python core/tools/candidates.py
python core/tools/candidates.py reject <candidate-id> --reason "<why not>" \
  --approved-by "<owner, date: approval quote>"
```

**Every write needs the owner's approval.** An agent may prepare the command and
show the expected record, but `add` / `promote` / `reject` / `archive` refuse to
run without `--approved-by` quoting the owner's decision. Same for claims:
`ClaimStore.add` requires `approved_by`.

A candidate is evaluated on val and protected from `dlef gc`; a claim is created
only after promotion and test eval. See `candidates/README.md` for the full
contract. `make report` renders the shortlist above the claims, and `make index`
regenerates the front door.

## Keeping the list small

- One experiment name per comparison group. Do not create an experiment per
  smoke test; use a single `debug` or `smoke` experiment for throwaway runs.
- A seed is a run dimension, not an experiment. Three seeds = three runs in the
  same experiment.
- Tag runs that must survive cleanup when you launch them:

  ```bash
  python core/commands/train.py --config input/configs/experiments/baseline/main.yaml \
    --tag baseline --tag reported
  ```

- Retention is `dlef gc`, dry-run by default:

  ```bash
  make gc-dry
  # inspect the plan, then add --apply
  python -m dlef.cli gc \
    --runs output/runs --sweeps output/sweeps \
    --keep-last 3 --keep-best 1 --metric-key mae \
    --keep-tag reported --keep-tag baseline \
    --sweep-ttl-days 30 --apply
  ```

Never `rm -rf output/runs/...`. `dlef gc` protects tagged runs, parents of kept
runs, sweep-referenced runs, active candidate runs and claim evidence.
`--sweep-ttl-days` also removes expired sweep records whose runs are no longer
kept; running sweeps are protected.
