# Candidates — the experiment shortlist

One JSON file per candidate: `output/candidates/<candidate_id>.json`.

A **candidate** is a named pointer to one or more runs that you have decided are
worth keeping and studying. It records *why* the run set matters and *what to
look at next*. It is the triage layer between the raw run store and the claims
you eventually report:

```text
output/runs/           dozens of runs from sweeps and one-offs
      │  scan with runs.py / TensorBoard
      ▼
output/candidates/     the few experiments worth thinking about
      │  compare on val, inspect slices, decide
      ▼
output/claims/         the numbers that go into the report
      │
      ▼
output/reports/        report.md
```

A candidate is **not** a claim:

| | Candidate | Claim |
|---|---|---|
| Question | "Is this worth studying?" | "What number do we report?" |
| Evidence | run ids (val metrics are enough) | eval ids → checkpoint → run |
| Test split | not required; usually avoided | frozen test benchmark required |
| Lifetime | changes status: candidate → promoted / rejected | final reported conclusion |
| Purpose | protect and organize promising runs | prove a reported number |

Candidates are evaluated on **val**. Test eval is spent only after promotion, so
the shortlist also protects the test set from repeated access.

## This folder is human-authored

Unlike `runs/`, `sweeps/` and `test_access/`, nothing here is generated by the
Runner. A human or agent writes candidates through
`CandidateStore` / `core/tools/candidates.py`. The files are small and should be
committed with the project; they are part of the experiment's memory.

## File format

| Field | Required | Meaning |
| --- | --- | --- |
| `candidate_id` | ✓ | unique name (= file name), e.g. `v11-ranksim-g20` |
| `title` | ✓ | one human-readable line |
| `run_ids` | ✓ | the evidence: one or more run ids; multi-seed = several ids |
| `status` | ✓ | `candidate`, `promoted`, `rejected`, `archived` |
| `reason` | ✓ | why it is shortlisted (or rejected) — judgment, not a metric |
| `next` | | what to inspect or do next |
| `metric` | | val metric key shown in the shortlist, e.g. `v11/worst_bin` (read from the latest `phase: "val"` record in each run's `metrics.jsonl`) |
| `experiment` | | display grouping; defaults to the first run's experiment |
| `claim_ids` | promoted | claims created from this candidate |
| `priority` | | sort order; lower comes first |
| `tags` | | free labels, e.g. `{"question": "ranking-loss"}` |
| `approved_by` | ✓ | the owner's approval, quoted with date/context; agents propose, the owner approves |
| `created_at` / `updated_at` | auto | timestamps |

`run_ids` is a **snapshot**. Creating a candidate from an experiment name
expands the runs at creation time; later runs do not silently join.

## Owner approval is required

The shortlist is the owner's decision, not the agent's. `add` / `promote` /
`reject` / `archive` all refuse to run without `--approved-by`, and that value
must quote the owner's explicit approval:

```bash
python core/tools/candidates.py add ... \
  --approved-by "twj 2026-11-18: v11-ranksim-g20 may enter the shortlist"
```

The workflow for an agent is:

1. prepare the exact command and the expected record (ids, reason, next);
2. ask the owner and wait for an explicit yes/no;
3. only then execute, with `--approved-by` quoting that decision.

An agent never writes `--approved-by` from its own judgment. The report and
`make index` show the approver for every candidate; records without one are
flagged as `UNAPPROVED` and cannot change status until the owner re-approves
them.

## Statuses

```text
candidate ──► promoted   has at least one claim; still protected from gc
    │
    └───────► rejected   closed with a reason; runs follow normal retention

promoted ──► archived    record kept, runs no longer protected by the candidate
```

| Status | Meaning | gc protection |
| --- | --- | --- |
| `candidate` | under review | ✓ |
| `promoted` | has claims | ✓ |
| `rejected` | not worth pursuing | ✗ |
| `archived` | closed / superseded | ✗ (claims still protect their evidence) |

A rejected candidate is not garbage: its `reason` is the memory of a dead end,
so the next person does not repeat it. The JSON can outlive the runs.

## Usage

```bash
# The shortlist (active candidates only)
python core/tools/candidates.py

# All candidates, including rejected/archived
python core/tools/candidates.py list --all

# One candidate with its runs and claims
python core/tools/candidates.py show v11-ranksim-g20
```

Shortlist a run set (owner approval):

```bash
python core/tools/candidates.py add \
  --id v11-ranksim-g20 \
  --title "RankSim + log target, 3 seeds" \
  --run <run_id_seed1> \
  --run <run_id_seed2> \
  --run <run_id_seed3> \
  --metric v11/worst_bin \
  --reason "best worst_bin so far; D cohort slightly worse, needs a look" \
  --next "per-bin MAE, then test eval if it holds" \
  --approved-by "twj 2026-11-18: v11-ranksim-g20 may enter the shortlist"
```

The tool prints warnings when a run is missing or when the run set spans more
than one experiment, but it does not guess. Every run id must resolve under
`output/runs/` at creation time.

Close a dead end (owner approval):

```bash
python core/tools/candidates.py reject v11-ranksim-g20 \
  --reason "D cohort regressed; not worth test access" \
  --approved-by "twj 2026-11-18: agreed, close it"
```

Promote a candidate after its claims exist (owner approval):

```bash
python core/tools/candidates.py promote v11-ranksim-g20 \
  --claim best-d-worst --claim best-d-lt10 \
  --approved-by "twj 2026-11-18: promote with the d-worst claim"
```

Promotion checks that every claim id exists in `output/claims/`. The order is
deliberate:

```text
1. compare candidates on val
2. ask the owner; record the approval
3. run test eval for the winner
4. create Claim(s) from the eval ids (approved_by required there too)
5. promote the candidate with those claim ids
```

Archive a candidate whose claims are stable and whose runs no longer need
candidate-level protection:

```bash
python core/tools/candidates.py archive v11-ranksim-g20 \
  --approved-by "twj 2026-11-18: archive it"
```

## Retention

`dlef gc` protects runs referenced by `candidate` and `promoted` candidates,
exactly like `baseline`/`reported` tags. The plan shows the reason:

```text
candidate:v11-ranksim-g20
```

Rejected and archived candidates do not protect their runs. Disable the whole
mechanism only for a deliberate cleanup:

```bash
python -m dlef.cli gc --runs output/runs --candidates output/candidates \
  --no-protect-candidates ...
```

## Rules

- One candidate = one configuration/lineage across seeds. Do not mix unrelated
  variants just because they scored well.
- Write a real `reason`; "good" is not a reason. State the question, the tradeoff
  or the anomaly you want to investigate.
- Do not auto-generate candidates from a metric ranking. A candidate is a
  judgment; a leaderboard is not a shortlist.
- Compare candidates on the same val protocol; test numbers appear only after
  promotion.
- Do not use a candidate to hide a failed run. Use `rejected` with a reason, or
  leave the run out of the shortlist.
- Never edit run directories or claims from this folder; candidates only point
  at them.
